01

企业年假审批系统

B 端 · 200+ 员工 6 周上线 药友制药（北京） 已上线

核心不是表单，是把审批链从代码里搬出来——组织架构变动时，HR 改配置而不是找开发改程序。

200+员工在用
1 周 → 1 天请假审批时效
3 天 → 1 小时HR 月度统计
问题

请假走邮件和 Excel：审批链写死在代码里，组织架构一调整就得改程序；年假额度靠 HR 手工算，口径不统一；员工不知道自己的单卡在谁那儿。

判断

访谈与问卷问了 200+ 名员工后，我把优先级从「做一个请假表单」改成「做一个可配置的流程引擎」：审批节点是数据，不是 if-else；再给 6 类角色各自的可见范围，让员工能看到「第 1/3 步、当前审批人是谁」。

取舍

6 周交付靠的是主动砍：先做申请主链路 + 额度计算 + 审批流转，报表和统计放二期；技术上选 Python + Flask + MySQL 的轻量架构，而不是上重型工作流引擎。

结果

上线后 200+ 员工使用，请假审批从 1 周压到 1 天，HR 月度统计从 3 天缩短到 1 小时；撤回、销假、转办、进度可见都跑通了。

02

医疗大模型 RAG 问答系统

AI 应用 课程复现 · 独立部署 三服务架构 PGVector + Qwen

一套「前端 → Java 业务 → Python 检索 → 本地大模型」的三服务系统。我完成的是从代码到线上可访问这一段，以及部署过程中对每条链路的取舍理解。

114 秒完整操作录屏
Top30 → 5双阶段检索
< 100ms交互响应
系统

Vue3 打包后由 Nginx 托管，/api 反代到 Spring Boot（JWT 鉴权、会话与历史、上传转发），再由 Java 调 Python（LlamaIndex 文档解析、PGVector 检索、BGE 重排、语义缓存），模型是本地 Ollama 上的 Qwen2.5:7b；MySQL 存业务数据，PostgreSQL + PGVector 存向量。

我做的

独立完成线上部署与排障：Nginx 反代与端口映射、跨域与 401 处理、上传超时调参、Ollama 模型加载与显存/内存约束、前后端与 Python 三段链路的联调。

我理解的取舍

为什么要重排（Top30 召回里噪声太多，Top5 才敢交给模型）；为什么要语义缓存（同类问题重复推理的成本与延迟）；为什么给用户「知识库范围」开关（不勾选就不知道答案从哪来，可信度无法解释）。

边界

教学版代码里有明文密码、硬编码 JWT 密钥、前后端上传上限不一致（50MB vs 30MB）等问题——真上生产要改的第一批就是这些，这也是我判断「能跑」和「敢给业务用」之间差距的依据。

检索Flask · LlamaIndex · PGVector · BGE
模型Ollama · Qwen2.5:7b（本地）

How I work

我怎么做事

两个作品背后是同一套方法，不是两段孤立的经历。

01 / 先定问题

把抱怨翻译成指标

员工说「审批慢」，我不直接做表单，而是拆成「等待时长、驳回率、HR 汇总工时」三个可测的数。指标定不下来，方案就没有对错，只有偏好。

02 / 再定边界

资源有限时做取舍

6 周上线靠的是主动砍功能：先做审批主链路 + 额度计算，报表放二期。我把「哪些不做」写进需求文档，比写「要做哪些」更能保护交付。

03 / 最后验证

自己动手跑一遍

系统能不能用，不是评审会上决定的。部署、联调、踩坑、记录报错，这些事我习惯自己做——它决定了我提需求时是否知道代价在哪。
